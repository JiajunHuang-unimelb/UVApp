# Current Location and UV Data Module

- Module: Foreground Location / GPS
- Initial development branch: `feat/gps-integration` (the implementation on `main` is authoritative)
- Status: Integrated into the application's actual data flow

## Scope

The current-location feature obtains a one-time foreground location fix through Google Fused Location and uses the coordinates to retrieve UV forecasts from Open-Meteo and reverse-geocoded place names from Nominatim. When the app is opened for the first time without an existing `locationFix`, `UVAppRoot` proactively invokes the location-permission entry point. Users can also request their current location manually from Home, Forecast, and Search.

Two location data flows must be distinguished:

- **Current-location lookup**: `FusedCurrentLocationProvider` obtains a one-time location fix and does not continuously subscribe to location updates.
- **Exposure-environment monitoring**: While an exposure session is running, `ExposureMonitoringService` may obtain continuous or adaptive location updates through a foreground service to determine whether the user is near a saved indoor location. This is separate from the one-time location flow handled by `FusedCurrentLocationProvider`.

The app declares foreground location and foreground-service permissions, but does not declare `ACCESS_BACKGROUND_LOCATION`.

```text
App starts without a locationFix, or the user taps the location action on Home / Forecast / Search
  → Location-permission entry point in UVAppRoot
  → MainViewModel.onUseCurrentLocation()
  → CurrentLocationProvider
  → FusedCurrentLocationProvider
  → LocationFix
  ├→ UvRepository.observeForecast() / refresh()
  │    → Room cache / Open-Meteo
  └→ PlaceRepository.reverseGeocode()
       → Room cache / Nominatim
  → MainUiState → Home / Forecast

User selects a search result in Search
  → MainViewModel.onPlaceSelected()
  → Fetch forecast for the selected place's coordinates (not treated as the device's actual GPS location)
```

## Location Retrieval Strategy

- Both Approximate and Precise location permissions are supported. Current-location lookup can proceed when only approximate location permission is granted.
- A normal current-location lookup first tries Google Fused Location's `lastLocation`. If no usable cached fix from the past five minutes is available, it directly requests a location with `PRIORITY_HIGH_ACCURACY`. The previous two-stage strategy of trying balanced power before switching to high accuracy is no longer used.
- Calls with `freshOnly = true` skip `lastLocation` and request a fresh, high-accuracy fix. This is mainly used when saving an indoor location requires fresh location evidence.
- The `CurrentLocationRequest` duration is set to **6 seconds**, and the overall `getCurrentLocation()` retrieval flow has a **7-second** coroutine timeout. These must not be described as 13 seconds.
- `MainViewModel` cancels preceding location requests and their associated forecast and place-name lookup jobs to prevent stale requests from overwriting a newer user selection.
- `DefaultUvRepository` reuses an existing forecast cache entry for a location within **1 km**. If that cache entry was fetched within the past **1 hour**, tapping Refresh will not trigger another Open-Meteo request. A network refresh is attempted only when no usable cache exists or the cache has expired.
- After a location fix succeeds, the app starts a UV forecast request and asynchronously performs Nominatim reverse geocoding. Failure to resolve a place name does not block the UV request. The current `MainViewModel` retains the latitude/longitude string generated by `coordinateLabel()` as the fallback place label.

`LocationFix` stores the following information:

- `latitude`, `longitude`: Geographic coordinates.
- `accuracyMeters`: Horizontal location accuracy, in metres.
- `capturedAtMillis`: Location capture time as a Unix timestamp in milliseconds.
- `isApproximate`: Whether only approximate location permission is available, or whether the fix is being treated as something other than the device's actual current location.
- `isMock`: Whether Android marks the location as a mock location.

## Permissions and Recovery

Location permission is not requested only after a button tap. When the app is first opened and `locationFix == null`, `UVAppRoot` proactively calls `requestCurrentLocation()`. Therefore, the system location-permission dialog may appear on first launch.

- **Permission not granted**: Use `RequestMultiplePermissions` to request `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION`.
- **Approximate location only**: Location and UV data can still be retrieved, and `LocationFix.isApproximate` is `true`.
- **Permission denied (not permanently)**: Report the denial to the UI. The user can tap the location action again or search for a place manually.
- **Permission permanently denied**: Tapping the location action again opens the app's system settings page.
- **Returning from system settings**: Recheck permissions in `ON_RESUME`. If a permission request was pending, continue the pending location lookup once permission is granted.
- **Device location disabled, timeout, or location unavailable**: Handle these separately using results such as `LocationDisabled`, `Timeout`, and `Unavailable`.

Manually selecting a place in Search is not equivalent to obtaining the device's current location. `MainViewModel.onPlaceSelected()` uses the coordinates of the search result and marks the resulting `LocationFix` with `isApproximate = true`, preventing the selected place from being treated as the user's actual location when evaluating indoor context.

## Privacy and Data Storage

- `AndroidManifest.xml` does not declare `ACCESS_BACKGROUND_LOCATION`. However, the exposure-monitoring service may continue monitoring location as a foreground service while the app UI is not visible. Therefore, the app must not be described as "never collecting location continuously."
- Current-location coordinates are sent to Open-Meteo for UV forecasts and may be sent to Nominatim for place-name lookup. User-facing data-source attribution and privacy information should accurately disclose this behavior.
- `uvapp.db` stores both UV/place-name caches and exposure history. **Exposure history is not a disposable temporary cache.**
- The current `backup_rules.xml` and `data_extraction_rules.xml` exclude the entire database from cloud backups and exclude the database under device-transfer rules. See `docs/exposure-tracking-api.md` for the implications of database clearing, uninstallation, and upgrade migrations for historical records.
- `MainViewModel.coordinateLabel()` currently uses a latitude/longitude string until place-name lookup succeeds, and when it fails. Therefore, it is no longer accurate to claim that "the production UI never displays full coordinates." If the product requirement is to hide coordinates, the fallback display logic must be changed separately.

## Automated Tests and Device Verification

The main location-related JVM tests currently enabled include:

- `LocationFixTest`: Checks valid ranges and boundary cases for coordinates, accuracy, and timestamps.
- `LocationFixValidatorTest`: Checks the accuracy, freshness, and abnormal timestamp handling of location evidence used for exposure monitoring.

The entire `MainViewModelTest` class is currently commented out. Its former test scenarios must not be presented as tests that have run and passed. For example, end-to-end behavior covering precise/approximate location integration, retaining UI data after a location timeout, and cancelling an older request when a new request begins still requires the relevant tests to be restored and rerun.

The following behaviors should also be verified on an Android emulator or physical device: the first permission request; granting Approximate location only; permission denial and permanent denial; returning from system settings; disabling device location services; obtaining an initial fix without a cache; reusing a cached location from the previous five minutes; switching between searched places; and location monitoring while an exposure session runs with the app in the background. This is a verification checklist, not a claim that all scenarios have passed.

## Known Limitations

- Failure of Nominatim does not directly cause the UV forecast request to fail; the current fallback place label may display a latitude/longitude string.
- Home and Forecast share forecast state. Live forecast retrieval and Room caching use the actual data layer, while `ForecastViewModel` manages date and time selection.
- `FusedCurrentLocationProvider` depends on Google Play services. If location services are unavailable, a current-location lookup may return `Unavailable`; the user can still select a place manually through Search.
- Manually tapping Refresh does not guarantee a network request, because cache entries from the past hour are reused first.
- Continuous location monitoring belongs to the exposure functionality in `ExposureMonitoringService` and must not be confused with the one-time location lookup triggered by the current-location action.
